# 0024 — 2D: sprites, atlases, tilemaps

- **Status:** implemented
- **Packages:** `@shard/sprite` (new), `@shard/render`, `@shard/texture`, `@shard/assets`, `@shard/project`
- **Depends on:** 0005, 0007, 0014, 0016

## Context

Shard is 2D and 3D natively. Today 2D means an orthographic camera looking at quads. A 2D game
needs sprites drawn by the hundred thousand in a handful of batches, texture atlases, frame
animation, and tilemaps. The 3D proof project needs the same pieces for HUD icons and minimaps,
and for world-space billboards (markers over waypoints, alien signage).

## Goals

- `Sprite`: a textured quad from a texture or an atlas region, with color, flip, anchor, and a size
  in world units or pixels.
- `TextureAtlas`: a data asset of named regions, built from a grid or from a packer at import
  (packing loose images into one texture).
- `SpriteAnimation`: frame sequences with frame rates, loop modes, and events.
- `Tilemap`: chunked tile layers over an atlas, rendered in a few draws, with per-tile flags (flip,
  rotate) and animated tiles.
- Sorting by layer and depth, and batching by texture, so draw calls scale with textures, not
  sprites.
- Pixel-perfect rendering on request: nearest filtering, texel snapping, integer scaling.

## Non-goals

- 2D lighting and shadows, normal-mapped sprites (their own spec, planned right after this one).
- 2D physics (M6, Rapier 2D).
- Skeletal 2D animation (Spine and similar) and nine-slice UI (M6 UI).
- Importing Tiled or LDtk files (a follow-up importer on this tilemap format).

## Design

### Components and assets

```ts
Sprite {
  texture: handle('Texture')          // or an atlas via `region`
  atlas: handle('TextureAtlas')       // optional
  region: string                      // atlas region name, e.g. "hero/idle_0"
  color: color, flipX: bool, flipY: bool
  anchor: vec2 = [0.5, 0.5]           // pivot in normalized sprite space
  size: vec2                          // world units; zero = texture/region size × Sprite2dSettings.pixelsPerUnit
  layer: i16                          // draw order band; within a band, sort by z then y (configurable)
}
SpriteAnimation { clip: handle('SpriteClip'), playing: bool, speed: f32, time: f32 }
TextureAtlas (asset): texture + regions { name: [x, y, w, h, pivotX?, pivotY?] }
SpriteClip (asset): atlas + frames [{ region, duration }] + loop: 'loop' | 'once' | 'ping-pong' + events
```

- Atlases come from `*.atlas.json` data assets (grid or explicit regions), or from an
  `atlas-pack` importer that packs a folder of PNGs (`sprites/hero/*.png` becomes `hero.atlas`)
  into one power-of-two texture with padding and edge extrusion.
- `SpriteClip` files (`*.clip.json`) reference an atlas's regions. A system advances animations in
  `Update` and sends `SpriteAnimationEvent` for frames that have events.

### Rendering

- Sprites extract into an instance buffer per (texture, blend) batch: position, size, rotation,
  UV rect, color. They're sorted by layer and depth and drawn instanced with one pipeline. Unchanged
  sprites keep their slots, following the 0022 pattern.
- Blending uses premultiplied alpha, so edges stay clean with bilinear filtering. Opaque sprites
  can go in an opaque batch with depth writes.
- The pass `sprites` runs after opaque 3D and before transparent 3D (world-space sprites), and a
  screen-space variant runs after tonemapping for overlay sprites (`Sprite2dSettings.space`).
- **Pixel-perfect:** `PixelPerfect { pixelsPerUnit, snap }` on a 2D camera renders to a
  low-resolution target and scales it up by an integer factor, with nearest sampling.

### Tilemaps

```ts
Tilemap { atlas: handle('TextureAtlas'), tileSize: vec2, chunkSize: u16 = 32, layer: i16 }
TilemapData (asset): layers [{ name, width, height, tiles: base64(Uint16) , flags?: base64(Uint8) }]
```

- Tile indices are atlas region indices (0 means empty). Flags are flip X, flip Y, and a 90°
  rotation.
- Each chunk becomes one instanced draw (tiles as instances) or, for static layers, one prebuilt
  vertex buffer. Only visible chunks are drawn. Editing a tile rebuilds only its chunk.
- `setTile(world, tilemap, x, y, index)` and `tileAt(...)` are the runtime API. Tilemap data files
  are validated (dimensions, indices within the atlas).

### Agent surface

- The components and assets have schemas, so agents author sprites, clips, and tilemaps as JSON
  and validate them.
- `asset.preview` of an atlas shows its regions outlined and labeled. A clip preview shows its
  frames.
- `render.describe` reports sprite batches, draw calls, and sprites per layer.

## Decisions

- **Premultiplied alpha everywhere.** It's the only blend that filters and composites correctly
  without dark fringes.
- **Atlases are data assets, and packing is an importer.** Agents can hand-write regions or drop
  images in a folder. Either way the result is one texture per atlas.
- **Tilemaps are chunked instance data.** Tilemaps with millions of tiles cost only what's on
  screen, and editing stays cheap.
- **The same renderer serves 2D and 3D.** Sprites are a pass in the same graph, so 2D games get the
  post stack and HDR for free, and 3D games get billboards.

## Acceptance criteria

- [x] 100k sprites from 4 atlases render at 60 fps at 1080p in at most 8 draw calls on the dev
      machine, and a static set uploads nothing after the first frame.
- [x] Sprites sort correctly by layer, then depth (golden image of overlapping sprites).
- [x] The atlas packer packs a folder of 50 images without overlaps, with extruded edges (no
      bleeding in a scaled golden image).
- [x] A `SpriteClip` plays at its frame durations (frame-stepped test) and sends its events.
- [x] A 1024×1024 tilemap draws only visible chunks (describe counts), and editing a tile updates
      only its chunk.
- [x] A pixel-perfect camera renders a sprite with crisp, integer-scaled texels (golden image).

## Implementation notes

- **Sprite fields beyond the design:** `blend` (`alpha`, `additive`, `opaque`) and `space`
  (`world`, `screen`) are per sprite, not in `Sprite2dSettings`. `Sprite2dSettings` holds
  `pixelsPerUnit` (default 100) and `sort` (`z`, or `y` for top-down scenes). An atlas region with
  its own pivot (not the center) replaces the sprite's `anchor`.
- **Sprites aren't lit.** They write their color straight into the pre-exposed HDR buffer, so they
  show at their texture's color whatever the exposure, and bloom and grading still apply. Screen
  sprites draw over the finished image (phase Overlay), positioned in pixels from the top left.
- **Rendering:**
  - Each sprite owns a slot in one buffer of 96-byte records (affine rows, uv rect, size, anchor,
    packed color). Records upload in dirty runs, and tables where nothing changed are skipped, as
    with meshes (0022).
  - Draw order is one sorted slot list: layer, then depth, then batch, so sprites sharing a layer
    and depth group by texture. It's a four-pass 16-bit radix sort that runs only when a key or
    batch changes.
  - A draw is a run of one batch (texture, blend, space) in that order.
  - Sprites aren't culled per view: the vertex stage is cheap enough at these counts.
  - Opaque sprites alpha-test at 0.5 and write depth. The others test against the scene's depth
    without writing it.
- **Premultiplied alpha:** `Texture.premultiplied` is new. KTX2 carries it (the DFD flag plus a
  key), the texture importer's `premultiplyAlpha` sets it, and the packer always does. Other
  textures are premultiplied in the shader after sampling.
- **Atlases:** `*.atlas.json` has `texture`, an optional `grid` (cells become regions
  `prefix0`, `prefix1`, …), and `regions: [{ name, rect, pivot }]`. The packer is
  `*.atlas-pack.json`: `{}` packs the images in the folder named like the file. Options are
  folder, padding (2), extrude (1), maxSize, and mipmaps.
  - Images are premultiplied in linear light, sorted by name, skyline-packed onto one
    power-of-two page (the packer moved from `@shard/text` to `@shard/texture`), with edges
    extruded into the padding.
  - To see the folder, `ImportContext.list(dir)` is new. It records the listing as a dependency,
    so adding or removing an image re-imports the atlas.
- **Clips:** `*.clip.json` has frames with durations, `loop` (`loop`, `once`, `ping-pong`), and
  `events: [{ frame, name }]`. A step that skips frames still sends their events. A `once` clip
  clears `playing` at its end.
- **Tilemaps:** `Tilemap` also has `data: handle('TilemapData')`. `TilemapData` has
  `animations: [{ tile, frames, frameTime }]` for animated tiles, and `TilemapData.create(w, h)`
  makes one in code.
  - Each layer is one chunk-major buffer of u32 tiles (index plus flags). Visible chunks go into a
    per-view list, and each layer is one instanced draw over them, using `firstInstance` to index
    that draw's part of the list. There are no prebuilt vertex buffers for static layers, because
    the instanced path was fast enough.
  - Edits go into a per-layer log that renderers turn into dirty chunks. Past 4096 edits between
    frames, layers re-upload whole.
- **Pixel perfect** lives in `@shard/render` (`PixelPerfect`), because it changes how cameras
  extract. The camera renders into a low-resolution target of `orthoHeight × pixelsPerUnit`
  texels. A second view (`pixel-perfect:<camera>`) scales it up by the largest whole number,
  letterboxed. With `snap`, the camera and sprite positions round to whole texels. Sprites under a
  pixel-perfect camera sample nearest.
- **Previews:** `@shard/assets` has a preview registry (`defineAssetPreview`), which
  `asset.preview` checks, so packages bring previews for their own types. An atlas shows its
  texture with regions outlined and numbered in a 3×5 pixel font. A clip shows its frames in a
  numbered row.
- **Projects:** `"sprite"` is a built-in manifest plugin (it includes `render/forward`). The
  generated docs have a `make-2d.md` skill. `render.describe` has a `sprites` section: sprites,
  batches, draw calls, sprites per layer, bytes uploaded, sorts, and tilemap chunks drawn and
  uploaded per view.
- **Measured:** the playground's `#sprites` demo is 100k sprites from 4 atlases under a panning
  camera, at 1920×1080 in Chrome on the dev machine (Apple M4). It runs at 60 fps with a 3.9 ms GPU
  frame, 4 draw calls, and 0 bytes uploaded per frame.
- **Found along the way:**
  - Bind groups cached at module level were keyed by buffer version, which every new app starts
    at 0, so a second app drew from the first one's buffers. The caches are per world now, keyed by
    buffer identity.
  - Tile-based GPUs skip empty passes along with their timestamps, which left stale stamps that
    stretched `gpu:frame` to seconds. The timer ignores stamps more than a second older than the
    frame's last one.
  - Found later by the physics demo (0028): growing the sprite record buffer lost every record
    uploaded before it, as with instances (0022). Growth now re-uploads every live record.
