# 0054 — Dice

- **Status:** accepted
- **Packages:** `@aethervtt/shard-dice` (new)
- **Depends on:** 0014, 0020, 0025, 0026, 0031, 0035, 0052, 0053, 0062, 0063

## Context

Aether, a VTT built on three.js, renders its own 3D dice. Its implementation includes procedural
polyhedra, canvas-painted face atlases, eleven skins built on shader families, deterministic Rapier
in a Worker, and a landing correction that shows the server's result without re-simulating. It
works, but every piece is host code. Moving Aether to Shard is the moment to make dice a
first-party engine package, so any Shard game with dice gets them.

Aether keeps what belongs to the game: the authoritative roll, the Chat entry, visibility, the
presentation queue, viewer preferences and cosmetic ownership. Everything else moves into
`@aethervtt/shard-dice`: geometry, face layouts, materials, effects, physics tracks, landing on a supplied
result, playback, quality, reduced motion, cancellation and cleanup. The package never decides a
result. It shows one.

## Goals

- Versioned, serializable **die definitions** for d4, d6, d8, d10, d12 and d20; **percentile**
  (a tens d10 and a units d10); and a single-body **d100**.
- **Face layouts** (numbers, pips, glyphs) as data, baked headless into an MSDF mark atlas.
- **Skins** as data assets that bind layouts, a dice material, per-type overrides, sounds and
  effect recipes. Material families are extensible materials (0020).
- **Fixed-step physical tracks** from 0053, independent of the result, so every viewer with the
  same request gets the same track.
- **Landing on an externally supplied result** by a symmetry correction of the mesh against the
  body.
- Playback with phases, dropped dice, reduced motion, three quality tiers up to a **32-die**
  large-pool path, cancellation and full resource cleanup.
- Fullscreen transparent output through 0052, and thumbnails and previews rendered on the same
  device.

## Non-goals

- Rolling or parsing formulas, visibility, queues, preferences, ownership. These belong to the host.
- Uploaded models or shaders. Skins reference registered definitions and families only, which
  keeps Aether's closed cosmetic vocabulary possible (Aether ADR-0095).

## Design

### Die definitions

A `DieDefinition` is a data asset (0031), `version: 1`:

```ts
interface DieDefinition {
  version: 1
  id: string                            // 'd20', 'd10-tens', 'd100-ball'
  sides: number
  vertices: Float32Array                // canonical, unit radius, fixed order
  read: 'face' | 'vertex'               // d4 reads its top vertex
  values: Record<string, number>        // sorted vertex ids of a face (or a vertex id) → value
  labels?: Record<number, string>       // value → printed mark ('00' … '90'; 10 → '0' on units)
  collider: 'hull' | 'ball'
  sizeMm: number                        // footprint before the presentation scale
  bevel: number
}
```

The engine computes faces, face frames (normal, tangent, bitangent) and the rotational symmetry
group once per definition and caches them by the definition's content hash. `values` keyed by
sorted vertex ids makes the numbering independent of hull iteration order. The validator checks
that every face has exactly one value, that there are no duplicates, and that opposite faces sum
to `sides + 1` where a definition opts in.

Built-ins: `d4`, `d6`, `d8`, `d10`, `d10-tens`, `d12`, `d20` (numbered as Aether's tables, so
existing rolls look the same) and `d100-ball`.

- **Percentile** is a request kind, not a definition. `{ kind: 'percentile', value }` plays one
  `d10-tens` and one `d10`. The value 100 shows `00` and `0`; the value 7 shows `00` and `7`.
- **d100** is a ball with 100 face cells laid out by a spherical Fibonacci spiral (flattened
  facets, numbers upright around the pole). Its collider is a ball, so every rotation is a
  symmetry, and the landing correction can put any cell up. Angular damping ramps up after the
  first bounce, so it settles in the same time as the others.

### Geometry and marks

`dieMesh(definition, skinOverrides)` builds a flat-shaded mesh with chamfered edges. Each face gets
a padded UV cell in a per-definition atlas. A vertex attribute tells face vertices from bevel
vertices, so one draw covers both.

Face marks are a `FaceLayout` asset: per value, a `text` (font handle, size, underline for 6 and
9), `pips`, or `glyph` (a registered vector path) mark, with a default for all values plus
per-value overrides. `bakeMarks(definition, layout)` writes one MSDF atlas using 0025's generator:
glyph outlines from the font, pips as analytic circles, and glyphs from their paths. Baking is
pure CPU, so it runs headless and in tests, and the result is cached by `(definition, layout)`
hash. Marks stay crisp at any die size because they're a distance field, not a painted bitmap.

### Materials and skins

`dice` is a material type that extends `standard` (0020). It adds the mark atlas, `markColor`,
`edgeColor`, mark depth (a bump taken from the distance field), `dropped` (a 0–1 blend toward the
skin's dropped look) and `result` (0 while tumbling, 1 once landed, for result-reactive families).
The package ships four families: `solid`, `resin` (translucent, with a tonal depth fake), `metal`
and `glass`. A host adds more with `defineDiceFamily(name, materialDefinition)`, which is
`defineMaterial` with the dice fields required. Aether's nebula, plasma, stained glass and black
hole families become such definitions in Aether's repo.

```ts
interface DiceSkin {                    // data asset, version 1
  version: 1
  id: string
  family: string
  params: Record<string, unknown>        // validated against the family's schema
  variants: Partial<Record<DieKind, { layout?: Handle; bevel?: number; params?: Record<string, unknown> }>>
  sounds?: { impact?: 'resin' | 'metal' | 'wood' | 'glass'; accent?: string }
  effects?: Handle[]                     // DiceEffectRecipe assets, at most 4
}
```

A skin that references a missing family, layout or recipe fails validation
(`dice/unknown-family` and so on). The host decides which skins exist; the package only renders
them.

### Tracks

`diceTrackScene(request)` turns a request into a 0053 `TrackScene`. It's deterministic in its
inputs: `seed`, tray (`halfWidth`, `halfDepth`), the ordered dice (definition id, scale, dropped),
optional launch edge, and the definitions' hashes. A seeded `Rng` from `@aethervtt/shard-core` chooses the
launch edge, lanes, velocities, spin and the starting orientations. **Target values aren't
inputs**, so a track can be recorded before the result is known and reused for any result.

Dropped dice get a heavier friction and a lower restitution, as in Aether. The settle rule
`dice-settle` ends the track when every body sleeps with a flat face (or, for d4, a vertex) up and
touching the floor. If that doesn't happen by step 240, it runs one cleanup phase: walls off,
die-to-die contacts off, and all bodies woken. A die outside the tray at the end, or a track that
hits `maxSteps` (480), falls back to a **placed** layout for that die. The die drops straight down
into its lane over the last 20 steps. That's honest and deterministic, and it never shows a cocked
or missing die.

`@aethervtt/shard-dice/worker` is the dice worker entry: 0053's `serveTracks` with `dice-settle` registered.

A host that wants every viewer to see the same throw passes a fixed tray (for example 5.4 × 3.15)
and lets the camera fit it. A host that wants the tray to follow each viewport passes that
viewport's tray. The package supports both, and the track's `sceneHash` records which was used.

### Landing on a supplied result

After recording, the natural value of each die is read from its final pose. `landingCorrection(def,
finalRotation, target, cameraUp)` picks, from the definition's symmetry group, the rotation that
maps the target's face frame onto the natural up frame. Among the candidates it takes the one whose
mark reads closest to screen-up. For the ball, the group is all rotations, and the twist is chosen
the same way. The correction is post-multiplied onto every sampled rotation of that die. Positions
and contacts are the physics track unchanged, so collisions still look right. A target the
definition can't show fails with `dice/invalid-value` before anything plays.

### Presentation

```ts
interface DiceRoll {
  id: string                               // the host's entry id; also the default seed
  dice: DiceRollDie[]
  total?: number
  source?: { mine: boolean; gm: boolean }
  tags?: string[]                          // host semantic tags, at most 8, for effect conditions
  seed?: string
  tray?: { halfWidth: number; halfDepth: number }
  quality?: 'auto' | 'full' | 'balanced' | 'large-pool'
  motion?: 'full' | 'reduced'
  effects?: boolean
  soundGain?: number                       // 0..1
}
interface DiceRollDie {
  kind: DieKind                            // 'd4' … 'd20' | 'd100' | 'percentile'
  value: number
  skin: Handle                             // a DiceSkin
  dropped?: boolean; high?: boolean; low?: boolean
}

const dice = world.resource(DiceTable)
const outcome = await dice.play(roll, { signal })   // 'finished' | 'dismissed' | 'cancelled' | 'failed'
dice.dismiss(); dice.shortenRest(ms); dice.phase     // 'idle' | 'simulating' | 'tumble' | 'accent' | 'rest'
```

`dicePlugin({ camera, restMs = 60_000, maxDice = 32 })` spawns a top-down camera, a shadow
catcher floor (0052), a key light and IBL. It owns one presentation at a time. `play()` while one
is active rejects with `dice/busy`, unless `{ replace: true }` is passed, which dismisses the
current one. Queuing is the host's. The presentation holds a frame demand (0052) from `play()`
until rest ends or it's dismissed, so an idle dice app requests no frames.

Playback samples the track at `elapsed / step` with `sampleTrack` into reused scratch, then writes
`Transform` columns. That's zero allocation per frame. Contacts feed the impact synth (`@aethervtt/shard-audio`
synthesized noise bursts, gain from `soundGain`), deduplicated as recorded.

**Dropped dice** use the skin's dropped look (`dropped = 1`: desaturated, 0.62 opacity, rougher, no
transmission), heavier physics, and are excluded from effects and attachments. Effect conditions
can still match `state: 'dropped'`.

**Reduced motion** skips physics entirely. Each die is placed in its lane, target face up with the
readable twist, and fades in over 150 ms. There is no tumble, and effects, attachments and lens
fields are off. Nothing is sent to the worker.

**Quality.** `resolveDiceQuality(count, preference)` picks a tier: `auto` becomes large-pool above
16 dice, `balanced` above 12, `full` above 24. Large-pool keeps the one directional shadow
static after landing (no moving shadows during the tumble; a contact blob instead), uses the
`solid` path of each family (no animated shaders, no separate mark mesh), turns off effects,
attachments and lens fields, and draws dice instanced by (definition, skin). Presentation scale
steps down with count (0.68, 0.56, 0.46, 0.38), as in Aether.

**Cancellation.** Aborting `signal` from any phase cancels the worker recording (0053), despawns
the presentation's entities, releases the frame demand, stops sounds, and resolves `'cancelled'`.
Any failure (worker crash, invalid value, device loss) resolves `'failed'` with a `ShardError` in
`dice.lastError`, never a half-played roll.

**Cleanup.** Meshes, mark atlases and materials are reference-counted by `(definition, skin)` and
released 8 s after their last use. `app.dispose()` (0052) releases everything at once. The package
creates no timers of its own; ambient animation at rest uses `FrameDemand.after`.

### Effects and attachments

A `DiceEffectRecipe` (data asset) is at most 8 conditions and 3 effects, with the same condition
vocabulary as Aether: die kind, value, face, `kept | dropped`, `high | low`, total comparisons,
source (`mine | gm | other`), and host tags. The effects are `light-pulse`, `particle-burst` (0026
CPU particles, at most 32) and `sound-accent`. Recipes play in the `accent` phase, seeded from the
roll id.

`defineDiceAttachment(name, factory)` registers a scene that attaches to a landed die (Aether's
accretion disk, say). The factory gets the die entity and returns entities parented to it, within a
declared vertex budget (at most 12k). The package spawns attachments after landing, at most 4 at a
time, and despawns them on dismissal, replacement, cancellation or teardown.

A die's recipe or attachment can publish **lens fields**: `LensFields` (`@aethervtt/shard-render`) is a
resource of up to 4 `{ screen: Vec2, radius, strength, ttlMs, source: Entity }`. Fields expire
unless refreshed. Views consume them through `lensPlugin` (0063).

### Aether parity

The families and skins Aether ships (nebula, tonal resin, stained glass, plasma, flame, precious,
cosmic, doodle, black hole) are ported in Aether's repository as `defineDiceFamily` materials and
`DiceSkin` assets. Each ported skin is approved through 0062: a Shard capture next to the current
three.js capture of the same roll (fixed seed and tray), approved with a reason for every visible
difference. Black Hole's distortion is part of that approval, through `lensPlugin` (0063). The package's
own acceptance covers the mechanisms; the skins' look is the port's gate.

### Previews

`renderDiceThumbnail(app, { skin, kind, value, size })` renders one landed die into an
`OffscreenTarget` on the app's device and resolves a texture or PNG bytes. `dice.preview(roll)` plays
a roll with a fixed seed and tray, for skin pickers. Neither creates a new GPU device or canvas.

### Baseline tier (0064)

The `dice` material, its four built-in families, playback, the shadow catcher and previews run on
the baseline tier. The large-pool tier's instanced draws become direct draws there. Host families
registered with `defineDiceFamily` must pass `shard validate` for baseline: accessors only, no raw
storage reads, no compute. That's what lets Aether's ported skins work for fallback users too.
Particle bursts use the CPU backend on baseline, as they already do for small counts.

### Agent surface

- `dice.describe`: phase, quality tier and its reason, dice with kind, value, natural value and
  correction, track steps, `settled`, `maxStepsHit`, placed-fallback dice, simulation ms, draw
  calls, live attachments, lens fields, and resource counts.
- `dice.play` / `dice.dismiss` through the protocol, and `shard screenshot` of a landed roll with a
  fixed seed, so an agent can check a skin or layout.
- Schemas for `DieDefinition`, `FaceLayout`, `DiceSkin` and `DiceEffectRecipe` under
  `.shard/schemas`.

## Decisions

- **Tracks don't depend on the result.** The landing correction makes that possible, and it means
  one recording per request, reusable and shareable between viewers.
- **Symmetry correction instead of re-simulating toward a target.** Searching seeds for a result
  is slow and visibly biased. Rotating the mesh by a symmetry of its own collider leaves the
  physics exactly as simulated.
- **A ball collider for d100.** A fair 100-face polyhedron doesn't exist, and fairness doesn't
  matter when the result is supplied. A ball makes every rotation a symmetry.
- **Reduced motion skips physics.** Aether simulates only to learn the natural face; placement
  doesn't need one.
- **MSDF marks instead of canvas atlases.** Headless, worker-safe, testable, and sharp at any size.
- **The package renders; the host decides.** Skins and families are registered by the host, so a
  closed cosmetic catalogue stays the host's policy.

## Acceptance criteria

- [ ] Every built-in definition validates, and its numbering is identical when its vertices are
      shuffled (as a hull would return them).
- [ ] For every definition, every value, and 50 seeds, the corrected final pose shows the target
      (read by `naturalValue` on the corrected rotation), and the mark reads within 45° of
      screen-up.
- [ ] Percentile shows `00`+`0` for 100 and `00`+`7` for 7. d100 shows every value 1–100.
- [ ] The same `DiceRoll` gives the same track hash in the worker and inline, and a golden hash.
      Changing only the values leaves the hash unchanged.
- [ ] 32 mixed dice settle or fall back to placed within 480 steps for 200 seeds, with no die
      outside the tray and no cocked die at rest.
- [ ] 32 d6 in the large-pool tier: playback allocates nothing per frame, and uses at most one
      instanced draw per (definition, skin) plus the floor, in `pnpm bench`.
- [ ] Reduced motion makes no worker call and shows the targets on the first rendered frame after
      the fade.
- [ ] Aborting in each phase resolves `'cancelled'` within one frame (simulating: within 10 ms),
      leaves no dice entities, and releases the frame demand.
- [ ] After `play`, rest, and 8 s idle, `gpu.stats('dice')` returns to its baseline. After
      `app.dispose()`, it's 0.
- [ ] A headless screenshot of a landed roll over a transparent clear has alpha 0 outside the dice
      and their shadows.
- [ ] Dropped dice get no effects or attachments. At most 4 attachments are ever alive.
- [ ] Reduced motion, effects off, the large-pool tier and disposal each publish no lens fields,
      and a published field expires `ttlMs` after its last refresh.
- [ ] A skin with an unknown family, a layout missing a value, or a recipe over its bounds fails
      validation with a path to the field.

## Open questions

- Should the package ship Aether's exact numbering tables as the built-ins? Proposed: yes, so
  rolls look the same during and after the migration.
- Should the tumble length be capped for large pools (for example 3 s, then the placed fallback)?
  Proposed: no, until measured.
