# 0054 — Dice

- **Status:** implemented
- **Packages:** `@aethervtt/shard-dice` (new), `@aethervtt/shard-physics`, `@aethervtt/shard-render`,
  `@aethervtt/shard-project`, `apps/playground`
- **Depends on:** 0014, 0020, 0025, 0026, 0031, 0035, 0052, 0053, 0062, 0063

## Context

Aether, a VTT built on three.js, renders its own 3D dice. Its implementation includes procedural
polyhedra, canvas-painted face atlases, eleven skins built on shader families, deterministic Rapier
in a Worker, and a landing correction that shows the server's result without re-simulating. It
works, but every piece is host code. Moving Aether to Shard is the moment to make dice a
first-party engine package, so any Shard game with dice gets them.

Aether keeps what belongs to the game: the authoritative roll, the Chat entry, visibility, the
presentation queue, viewer preferences and cosmetic ownership. Everything else moves into
`@aethervtt/shard-dice`: geometry, face layouts, materials, effects, physics tracks, landing on a supplied
result, playback, quality, reduced motion, cancellation and cleanup. The package never decides a
result. It shows one.

## Goals

- Versioned, serializable **die definitions** for d4, d6, d8, d10, d12 and d20; **percentile**
  (a tens d10 and a units d10); and a single-body **d100**.
- **Face layouts** (numbers, pips, glyphs) as data, baked headless into an MSDF mark atlas.
- **Skins** as data assets that bind layouts, a dice material, per-type overrides, sounds and
  effect recipes. Material families are extensible materials (0020).
- **Fixed-step physical tracks** from 0053, independent of the result, so every viewer with the
  same request gets the same track.
- **Landing on an externally supplied result** by a symmetry correction of the mesh against the
  body.
- Playback with phases, dropped dice, reduced motion, three quality tiers up to a **32-die**
  large-pool path, cancellation and full resource cleanup.
- Fullscreen transparent output through 0052, and thumbnails and previews rendered on the same
  device.

## Non-goals

- Rolling or parsing formulas, visibility, queues, preferences, ownership. These belong to the host.
- Uploaded models or shaders. Skins reference registered definitions and families only, which
  keeps Aether's closed cosmetic vocabulary possible (Aether ADR-0095).

## Design

### Die definitions

A `DieDefinition` is a data asset (0031), `version: 1`:

```ts
interface DieDefinition {
  version: 1
  id: string                            // 'd20', 'd10-tens', 'd100-ball'
  sides: number
  vertices: Float32Array                // canonical, unit (circum)radius, fixed order
  read: 'face' | 'vertex'               // d4 reads its top vertex
  values: Record<string, number>        // sorted vertex ids of a face (or a vertex id) → value
  labels?: Record<number, string>       // value → printed mark ('00' … '90'; 10 → '0' on units)
  collider: 'hull' | 'ball'
  sizeMm: number                        // footprint before the presentation scale
  bevel: number
  markScale?: number                    // preferred mark height, of a face's size (shrunk to fit)
  oppositesSum?: boolean                // opposite faces must sum to sides + 1
}
```

The engine computes faces, face frames (normal, tangent, bitangent) and the rotational symmetry
group once per definition and caches them by the definition's content hash. `values` keyed by
sorted vertex ids makes the numbering independent of hull iteration order. The validator checks
that every face has exactly one value, that there are no duplicates, and that opposite faces sum
to `sides + 1` where a definition opts in (`oppositesSum`: the d6, d8, d12 and d20; a d10's printed
digits sum to 9, so it doesn't).

A value's mark reads up toward the one vertex farthest from its face's center (a kite's apex),
else toward a vertex (triangles, pentagons), else toward the middle of an edge (squares). That's
chosen on the lowest value's face; every other face gets it carried there by a symmetry, so all
marks sit alike. A d4 reads its top vertex: each face prints the value of each of its corners near
that corner, reading toward it.

Built-ins: `d4`, `d6`, `d8`, `d10`, `d10-tens`, `d12`, `d20` (numbered as Aether's tables, with
Aether's vertex orders, so existing rolls show the same faces) and `d100-ball`. Mark orientation
follows the rule above rather than Aether's, a visible difference the skins' 0062 approvals cover.
`defineDie` registers more; `dice/DieDefinition` files (`*.die.json`) describe them as data.

- **Percentile** is a request kind, not a definition. `{ kind: 'percentile', value }` plays one
  `d10-tens` and one `d10`. The value 100 shows `00` and `0`; the value 7 shows `00` and `7`.
- **d100** is a ball with 100 face cells laid out by a spherical Fibonacci spiral (flattened
  facets, numbers upright around the pole). Its collider is a ball, so every rotation is a
  symmetry, and the landing correction can put any cell up. Angular damping ramps up after the
  first bounce, so it settles in the same time as the others.

### Geometry and marks

`dieMesh(definition, bevel)` builds a flat-shaded mesh with chamfered edges: faces inset toward
their centers, strips along the edges and caps at the corners, with radial normals on the chamfer
so its triangulation doesn't flash. Each face gets a padded UV cell in a per-definition atlas. A
vertex attribute (`uv1.x`: 1 on faces, 0 on the chamfer; `uv1.y` the face) tells face vertices
from bevel vertices, so one draw covers both.

Face marks are a `FaceLayout` asset (`*.dice-layout.json`): per value, a `text` (font handle, size,
weight, underline), `pips` (1 to 9), `glyph` (a registered vector path) or `blank` mark, with a
default for all values plus per-value overrides. Text without a font prints the built-in
numerals, Inter's digits (OFL) as outlines, so layouts bake with no font asset. `underline:
'auto'` underlines a label that reads as another of the die's labels turned around: 6 and 9 on a
d20, 16 and 91 on the d100, but not a d8's 6, which has no 9 to be taken for.
`bakeMarks(definition, layout)` writes one MSDF atlas using 0025's generator: glyph outlines from
the font, pips as analytic circles, and glyphs from their paths (`defineDiceGlyph(name, { path,
viewBox })`, SVG path data; six built-ins). Upright characters are baked once per (character,
size) and placed on whole pixels, so a d100's hundred labels share ten digits. Where two pieces'
fields overlap (the digits of a condensed "20"), the texel keeps the larger median in all three
channels, a plain distance field there: keeping one piece's channels would set texels of two
fields side by side, and filtering between them draws cracks. Baking is pure CPU, so it runs
headless and in tests, and the result is cached by `(definition, layout)` hash. Marks stay crisp
at any die size because they're a distance field, not a painted bitmap.

Marks keep their ink on the flat face. `markPlacements(definition, layout)` puts each mark at the
deepest point of its region: the face with its corners pulled in by the bevel, or on a d4 each
corner's share of it (the kite from the face's center to the midpoints of the corner's edges). The
mark is drawn at `markScale`, unless its outline (control points, underline and weight included)
would come within `MARK_MARGIN` (12%) of the region's inscribed radius of an edge: then every mark
of the die shrinks by one factor, so its numbers stay alike. Roomy faces keep `markScale` (d6,
d12); a d20's "20" and a d10's "10" set their dice's size.

### Materials and skins

Every dice family is a material type that extends `standard` (0020) with the dice fields: the
mark atlas, `markColor`, `markEmissive`, `markRoughness`, `markMetallic`, `markDepth` (a bump taken
from the distance field), `edgeColor` and `edgeMix` (the chamfer), `droppedColor` and `dropped` (a
0–1 blend toward the skin's dropped look), `fade`, `result` (0 while tumbling, 1 once landed,
ramped over 350 ms, for result-reactive families) and `resultTime` (the shader clock,
`globals.time`, when the dice landed: reactions animate from `globals.time − resultTime`). The
package ships four families:

- `dice/SolidDice`: an opaque body, flecks in the pour.
- `dice/ResinDice`: a tonal depth fake: deep color face-on, light at grazing angles and on the
  chamfer, swirl, the result face lit once landed. Opaque unless `resinOpacity` is below 1.
- `dice/MetalDice`: brushed, worn bright at the edges, enamel marks.
- `dice/GlassDice`: see-through; clear face-on, bright rims, opaque marks.

A host adds more with `defineDiceFamily(name, { fields, surface | shader, blend, translucent,
animated })`, which is `defineMaterial` with the dice fields required. `surface` is a WGSL snippet
shading the body, wrapped in a generated `pbr_input` that runs the shared `dice_finish` after it
(marks, chamfer, dropped look, fade, from `shard::dice::surface`); `shader` is a whole module
instead. A surface has `globals.time` and the library's helpers: `dice_hash`, `dice_noise`,
`dice_fbm`, `dice_luma`, and `dice_local_ray(in, local)`, the view ray inside the die (recovered
from how world and object positions change across the pixel), for what's seen through its glass.
`translucent(params)` says a skin's dice are see-through (they blend); `blend` fixes a blend for
families that only work blended. `animated` (`true`, or `{ fps }`) says the body moves with time:
while its dice are on the table, frames keep coming at the display's rate (the `dice/animated`
demand) or at most `fps` (`FrameDemand.after`); never under reduced motion.
Aether's nebula, plasma, stained glass and black hole families become such definitions in
Aether's repo. The playground's dice page defines a nebula and, after Aether's, an animated black
hole, pulsar and quasar this way, with the black hole's accretion disk as an attachment.

The tray floor is `dice/DiceTray`: a shadow catcher (0052, through `shadow_visibility`, now shared
in `shard::pbr::catcher`) that also draws contact blobs. The floor and every blob are instances of
one quad with this one material (a blob's `InstanceData.x` is its strength), so they're one draw.
Blended dice (glass, see-through resin, dropped, fading) cast no shadow, so they get a blob,
leaning toward where the key light's shadows fall.

```ts
interface DiceSkin {                    // data asset (*.dice-skin.json), version 1
  version: 1
  id: string
  family: string                         // 'dice/SolidDice', or a host family
  params: Record<string, unknown>        // validated against the family's schema
  variants: Record<DieKind, { layout: Handle | null; bevel: number; params: Record<string, unknown> }>
  sounds: { impact: 'resin' | 'metal' | 'wood' | 'glass'; accent: '' | AccentCue }
  effects: Handle[]                      // DiceEffectRecipe assets, at most 4
}
```

`validateDiceSkin(skin, { layout, recipe })` returns every problem, each with a path into the
skin: `dice/unknown-family` (`/family`); parameters the family doesn't have, or ones the package
sets itself (`marks`, `dropped`, `fade`, `result`, `resultTime`); a layout that can't show a value of its kind
(`dice/layout-missing-value` at `/variants/d20/layout/default`: pips on a d20); more than 4
recipes; a recipe over its bounds (`dice/recipe-bounds` at `/effects/0/conditions`). A variant with
no layout prints numbers (pips on a d6). The package ships six skins (`DICE_SKINS`: ivory,
obsidian, teal, ember, brass, frost) for previews, tests and quick starts. The host decides which
skins exist; the package only renders them.

### Tracks

`diceTrackScene(request)` turns a request into a 0053 `TrackScene`. It's deterministic in its
inputs: `seed`, tray (`halfWidth`, `halfDepth`), the ordered dice (definition id, scale, dropped),
optional launch edge, and the definitions' hashes. A seeded `Rng` from `@aethervtt/shard-core` chooses the
launch edge, lanes, velocities, spin and the starting orientations. **Target values aren't
inputs**, so a track can be recorded before the result is known and reused for any result.
Every number in the scene comes from +, −, ×, ÷ and √ on the Rng's draws, which IEEE 754 rounds
the same everywhere: starting rotations are points in the 4D ball, normalized, and the d10's
vertices are written out rather than computed with `Math.cos`.

Dropped dice get a heavier friction and a lower restitution, as in Aether. The settle rule
`dice-settle` ends the track when every body in the tray sleeps with a flat face (or, for d4, a
vertex) up and touching the floor; a die that left the tray doesn't hold it up. When every body
sleeps with one cocked, or it hasn't settled by step 240, it runs one cleanup phase: walls off,
die-to-die contacts off, and all bodies woken. A ball's angular damping ramps from 0.2 to 8 over
20 steps after its first bounce (a 0053 `TrackPhase.damping`, one per step). A die outside the tray
at the end, or not resting flat when a track hits `maxSteps` (480), falls back to a **placed**
layout: the free grid spot nearest where it ended. The die drops straight down into it over the
last 20 steps, target up and upright. That's honest and deterministic, and it never shows a
cocked or missing die. The rule gets what it needs as data (`diceSettleParams`), since the worker
has no registries.

`@aethervtt/shard-dice/worker` exports `diceWorker()`, which starts the dice worker entry: 0053's
`serveTracks` with `dice-settle` registered.

A host that wants every viewer to see the same throw passes a fixed tray (for example 5.4 × 3.15)
and lets the camera fit it. A host that wants the tray to follow each viewport passes that
viewport's tray. The package supports both, and the track's `sceneHash` records which was used.

### Landing on a supplied result

After recording, the natural value of each die is read from its final pose. `landingCorrection(def,
finalRotation, target, cameraUp)` picks, from the definition's symmetry group, the rotation that
maps the target's face frame onto the natural up frame. Among the candidates it takes the one whose
mark reads closest to screen-up. For the ball, the group is all rotations, and the twist is chosen
the same way. The correction is post-multiplied onto every sampled rotation of that die. Positions
and contacts are the physics track unchanged, so collisions still look right. A target the
definition can't show fails with `dice/invalid-value` before anything plays.

The symmetries that keep a face on top turn its mark in steps of 360° over their count, so the best
one reads within half a step of screen-up: 45° on a d6, 36° on a d12, 60° on a d4, d8 and d20,
exactly on the d100. A d10's kites have no symmetry about their own normal, so its mark reads the
way the throw left it, as a real d10's does.

### Presentation

```ts
interface DiceRoll {
  id: string                               // the host's entry id; also the default seed
  dice: DiceRollDie[]
  total?: number
  source?: { mine: boolean; gm: boolean }
  tags?: string[]                          // host semantic tags, at most 8, for effect conditions
  seed?: string
  tray?: { halfWidth: number; halfDepth: number }
  launch?: 'left' | 'right' | 'top' | 'bottom'
  quality?: 'auto' | 'full' | 'balanced' | 'large-pool'
  motion?: 'full' | 'reduced'
  effects?: boolean
  soundGain?: number                       // 0..1
}
interface DiceRollDie {
  kind: DieKind                            // 'd4' … 'd20' | 'd100' | 'percentile'
  value: number
  skin: Handle                             // a DiceSkin
  dropped?: boolean; high?: boolean; low?: boolean
}

const dice = world.resource(DiceTable)
const outcome = await dice.play(roll, { signal })   // 'finished' | 'dismissed' | 'cancelled' | 'failed'
dice.dismiss(); dice.shortenRest(ms); dice.phase     // 'idle' | 'simulating' | 'tumble' | 'accent' | 'rest'
```

`dicePlugin({ camera, restMs = 60_000, maxDice = 32, worker, now })` spawns a top-down camera
(framing the tray, screen-up toward −z), the tray floor, a key light and IBL (a small procedural
studio, reflected by metal and glass, never shown). `worker` is `diceWorker`, or `'inline'` (the
default, for Node and the CLI). It owns one presentation at a time. `play()` while one is active
rejects with `dice/busy`, unless `{ replace: true }` is passed, which dismisses the current one.
Queuing is the host's. The presentation holds a frame demand (0052) while it moves: from `play()`
through the tumble, the accent and the result ramp. At rest it asks for frames only through
`FrameDemand.after` (the rest's end), so a resting table, like an idle one, requests no frames,
unless its dice are of an animated family.

Playback samples the track at `elapsed / step` with `sampleTrack` into reused scratch, then writes
`Transform` columns (and the blobs' `InstanceData`). That's zero allocation per frame.

**Sound.** Contacts, as the track recorded them, play impacts synthesized once per material
(resin, metal, wood, glass) into WAV clips: modal, not noise bursts. An impact is the die's few high
modes (damped sines, jittered per variation), excited through a contact that's shorter the harder
the hit, so hard hits ring bright and soft ones dull; a short band-passed clack; and on the tray a
low knock. Each material bakes three strength layers of six variations, tray and die-to-die (two
bodies, no knock), while the worker records, and preloads them (0035's `preloadSound`), so the
first impacts start on time. Each impact takes a variation from the roll's seed and plays at a
pitch and level picked around the contact's (0035's ranges, ±6% and −20%): no two alike. Level
grows as strength^1.5 (light touches stay light), pitch goes with the die's size (bigger rings
lower). A die sounds at most every 45 ms, and a frame plays at most its four strongest contacts,
so a pool rattles instead of firing. Accent cues play a little above the hardest impact. A placed
die lands with a knock of its own.

**Dropped dice** use the skin's dropped look (`dropped = 1`: toward `droppedColor`, 0.62 opacity,
rougher, no transmission) from the start, through a blended variant of their material, get the
heavier physics, and are excluded from effects and attachments. Effect conditions can still match
`state: 'dropped'`.

**Reduced motion** skips physics entirely. Each die is placed in its lane (rows centered in the
tray), target face up with the readable twist, and fades in over 150 ms through a blended variant
of its material, a contact blob under it. There is no tumble, and effects, attachments and lens
fields are off. Nothing is sent to the worker.

**Quality.** `resolveDiceQuality(count, preference)` picks a tier and says why: `auto` is full up to
12 bodies, balanced to 16, then large-pool; `balanced` holds to 12 and `full` to 24 before
large-pool takes over. Full has moving shadows, family shaders, effects, attachments and lens
fields; balanced is full without attachments and lens fields. Large-pool keeps the one
directional shadow static after landing (no moving shadows during the tumble; a contact blob
instead), turns off effects, attachments and lens fields, and draws dice instanced by (definition,
skin): a die's value rides in `InstanceData`, so one material serves every die of a kind and skin.
Dice keep their skin's family; see-through families draw opaque, so they batch (a family with a
fixed `blend` can't, and stays blended). As a large pool lands, its shadow fades in on the tray
over the result ramp while the opaque dice's blobs fade out; its dice don't receive shadows, so
they don't darken when shadows switch on. Presentation scale steps down with count (0.68, 0.56,
0.46, 0.38), as in Aether.

**Cancellation.** Aborting `signal` from any phase cancels the worker recording (0053), despawns
the presentation's entities, releases the frame demand, stops sounds, and resolves `'cancelled'`.
Any failure (worker crash, invalid value, device loss) resolves `'failed'` with a `ShardError` in
`dice.lastError`, never a half-played roll.

**Cleanup.** Meshes, mark atlases and materials are reference-counted by `(definition, skin, kind)`
and released 8 s after their last use (`GpuAssets.releaseMesh`, and the new `releaseTexture` and
`releaseMaterial`, destroy their GPU copies). `app.dispose()` (0052) releases everything at once.
The package creates no timers of its own: the release and the rest's end are `FrameDemand.after`
asks.

### Effects and attachments

A `DiceEffectRecipe` (data asset, `*.dice-effect.json`) is at most 8 conditions and 3 effects, with
the same condition vocabulary as Aether: die kind, value, face (the printed label, `'00'`),
`kept | dropped`, `high | low`, total comparisons, source (`mine | gm | other`), and host tags. The
effects are `light-pulse`, `particle-burst` (0026 CPU particles, at most 32), `sound-accent`,
`lens-pulse` (a lens field on the die, ramped over its duration) and `attachment` (a registered
attachment on each die the recipe anchors to). Recipes play in the `accent` phase, seeded from the
roll id: at most 4 per roll, each once however many skins carry it. A recipe's conditions read the
whole roll; its positional effects and attachments anchor to the kept dice whose skin carries it
and that meet its die conditions (every such die when it has none). Dropped dice never anchor.

`defineDiceAttachment(name, { vertices, spawn, update })` registers a scene that attaches to a
landed die (Aether's accretion disk, say). `spawn` gets the die entity and returns entities
parented to it, within a declared vertex budget (at most 12k); `update` runs each frame it lives and
says when it's done. The package spawns attachments after landing, at most 4 at a time, and
despawns them on dismissal, replacement, cancellation or teardown.

A die's recipe or attachment can publish **lens fields**: `LensFields` (`@aethervtt/shard-render`) is a
resource of up to 4 `{ screen: Vec2, radius, strength, ttlMs, source: Entity }`. Fields expire
unless refreshed. Views consume them through `lensPlugin` (0063). An attachment publishes with
`ctx.lens({ radius, strength, ttlMs })`, centered on its die in the dice view's CSS pixels; a
presentation clears its dice's fields when it ends.

### Aether parity

The families and skins Aether ships (nebula, tonal resin, stained glass, plasma, flame, precious,
cosmic, doodle, black hole) are ported in Aether's repository as `defineDiceFamily` materials and
`DiceSkin` assets. Each ported skin is approved through 0062: a Shard capture next to the current
three.js capture of the same roll (fixed seed and tray), approved with a reason for every visible
difference. Black Hole's distortion is part of that approval, through `lensPlugin` (0063). The package's
own acceptance covers the mechanisms; the skins' look is the port's gate.

### Previews

`renderDiceThumbnail(app, { skin, kind, value, size, output })` renders one landed die, seen from
above at an angle, into an `OffscreenTarget` on the app's device, waits for a complete frame (one
that doesn't hold `render/loading`), and resolves PNG bytes (straight alpha) or the texture.
`dice.preview(roll)` plays a roll with a fixed seed and tray, for skin pickers. Neither creates a
new GPU device or canvas.

### Baseline tier (0064)

The `dice` material, its four built-in families, playback, the shadow catcher and previews run on
the baseline tier, on WebGPU's compatibility mode and on WebGL2 (a 32-die roll passes the fixture's
plan there). The large-pool tier's instanced draws are direct draws there, from the instance data
texture. Host families registered with `defineDiceFamily` must pass `shard validate --tier
baseline`: `@data` declarations only, no raw storage reads, no compute. That's what lets Aether's
ported skins work for fallback users too. Particle bursts use the CPU backend on baseline, as they
already do for small counts. `shard shaders bake` covers skins no scene shows through
`shaders.variants.json`'s `{ "dice": { "skins": "*", "kinds": "*" } }` entries: every skin as
each kind, opaque and blended.

### Agent surface

- `dice.describe`: phase, quality tier and its reason, the animated rate (`'display'`, an fps, or
  null); each die's kind, value, label, natural
  value (the physics' face), shown value (what's on top now) and correction; the track's hash,
  steps, `settled`, `maxStepsHit`, simulation ms and contacts; placed-fallback dice; matched
  recipes; draw calls; live attachments; lens fields; resource counts; GPU objects; worker
  recordings.
- `dice.play { roll, replace, wait }` / `dice.dismiss` through the protocol, and `shard screenshot`
  of a landed roll with a fixed seed: a scene entity with `dice/RollRequest { roll }` plays it (with
  `"plugins": ["dice"]` in `shard.json`), so an agent can check a skin or layout. Dice on the table
  are `dice/Die` entities.
- Schemas for `DieDefinition`, `FaceLayout`, `DiceSkin` and `DiceEffectRecipe` under
  `.shard/schemas` (`die`, `dice-layout`, `dice-skin`, `dice-effect`).

## Decisions

- **Tracks don't depend on the result.** The landing correction makes that possible, and it means
  one recording per request, reusable and shareable between viewers.
- **Symmetry correction instead of re-simulating toward a target.** Searching seeds for a result
  is slow and visibly biased. Rotating the mesh by a symmetry of its own collider leaves the
  physics exactly as simulated.
- **A ball collider for d100.** A fair 100-face polyhedron doesn't exist, and fairness doesn't
  matter when the result is supplied. A ball makes every rotation a symmetry.
- **Reduced motion skips physics.** Aether simulates only to learn the natural face; placement
  doesn't need one.
- **MSDF marks instead of canvas atlases.** Headless, worker-safe, testable, and sharp at any size.
- **The package renders; the host decides.** Skins and families are registered by the host, so a
  closed cosmetic catalogue stays the host's policy.
- **Track inputs are trig-free.** Node's and Chromium's V8 round `sin` and `cos` differently in the
  last bit, and one bit in an input is another track. +, −, ×, ÷ and √ round the same everywhere.
- **The tray draws its own blobs.** A shadow catcher that also draws contact blobs, the floor and
  every blob one instanced draw, keeps a large pool at one draw per (definition, skin) plus the
  tray, and gives blended dice, which cast no shadow, some ground.
- **Blended variants for dropped and fading dice.** Opacity needs blending, and switching a
  material's blend mode mid-roll would compile a pipeline mid-roll. A die's look is fixed when it
  spawns.
- **A readable twist within the symmetry.** The acceptance criterion first asked for 45° on every
  die, which only a d6 (or better) can give; a turn outside the symmetry group would move the die
  against its own contacts.
- **Modal impacts, varied at playback.** The first impacts were noise bursts through a low-pass,
  one level each, spaced by one clock across all dice: they read as popcorn, or gunfire. Dice
  ring: a few high modes, brighter the harder the hit. Variety comes from baked variations and
  from 0035's pitch and volume ranges, which any game's repeated sounds want too.
- **Marks fit their faces.** A fixed share of a face's bounding square put a d20's "20" over its
  edges (the square is twice a triangle's inscribed circle). Fitting the ink to the flat face, one
  scale per die, keeps every definition's marks inside without tuning each `markScale`.
- **Large pools keep their skins.** Drawing every family through the solid one saved nothing:
  draws are per (definition, skin) either way, and small dice cost few pixels. What costs is
  blending (sorted, one draw per die), so see-through families draw opaque there instead.
- **Animated families say so.** A resting table draws nothing, so a body moving with
  `globals.time` would freeze once dice land. `animated` keeps frames coming for exactly those
  families, at the rate they ask; `resultTime` gives their reactions a clock.

## Acceptance criteria

- [x] Every built-in definition validates, and its numbering is identical when its vertices are
      shuffled (as a hull would return them).
- [x] For every definition, every value, and 50 seeds, the corrected final pose shows the target
      (read by `naturalValue` on the corrected rotation), and the mark reads as close to
      screen-up as the definition's symmetry allows: within half a step of it (45° on a d6, 36° on a
      d12, 60° on a d4, d8 and d20, exact on the d100), no other symmetry doing better.

## Implementation notes

- **Package:** `packages/dice`. `definition.ts`, `hull.ts` and `builtins.ts` (definitions, faces,
  symmetry groups, frames); `landing.ts`; `track.ts` and `settle.ts` (the rule on its own, so the
  worker carries nothing else: the `dice-worker` size fixture is 5.6 KB brotli beyond Rapier, and
  `budgets.json` forbids render and GPU code in it); `numerals.ts`, `glyphs.ts`, `layout.ts`,
  `cells.ts`, `marks.ts` (the bake); `mesh.ts`; `material.ts`, `families.ts`, `tray.ts`;
  `skin.ts`, `effects.ts`, `attachments.ts`, `sound.ts`; `resources.ts`, `quality.ts`, `roll.ts`,
  `table.ts` (the presentation), `plugin.ts`, `methods.ts`, `preview.ts`, `studio.ts`.
- **Measured** on the dev machine: a 32-die track records in about 20 ms; a single die settles in
  about 1.5–2.5 s of track (the ball's p50 now 138 steps, a d20's 136). Bakes take 5–60 ms for
  d4 to d20 and about 95 ms for the d100, once per (definition, layout). In Chromium, the 32-die
  scenario ran at a p95 frame time of 6.2 ms (a 165 Hz display), GPU p95 0.34 ms, no long tasks.
- **Engine changes:** 0053's `TrackPhase` gains `damping` (per body, from the next step). The
  shadow catcher's visibility is `shard::pbr::catcher::shadow_visibility`, shared with the tray.
  `GpuAssets` gains `releaseTexture` and `releaseMaterial`. Project manifests can name `dice`.
  0035 gains pitch and volume ranges (`playSound`'s `[min, max]`, `AudioSource.pitchRandom` and
  `volumeRandom`) and `preloadSound` (an optional `AudioBackend.preload`).
- **Demo:** `apps/playground/dice.html`: a VTT-shaped page with the dice over everything, a roll
  builder and quick rolls, skin thumbnails rendered on the dice app's device, the presentation
  options, a chat log of the host's results, `dice.describe` live, the golden check, and host
  families: a nebula (animated at 30 fps), and in `dice-cosmic.ts` Aether's black hole (a vortex
  and lensed stars inside the glass, collapsing on a natural 1), pulsar and quasar (flaring on a
  20, fracturing on a 1). Their natural 20s attach Aether's result scenes as camera-facing
  windows: the black hole's ray-traced accretion disk (the far side behind the die's middle, the
  near side over it) with a lens field that bends the table, the pulsar's lighthouse beam, and the
  quasar's turbulent disk and one-sided jet. A window nearer the camera than the die is moved
  along the line from the camera and scaled by how much nearer it got, so the halves line up
  wherever the die lands.
